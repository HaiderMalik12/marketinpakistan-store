# CLAUDE.md

This is the marketinpakistan retail store — a Next.js site for a family fashion business in Faisalabad, Pakistan, selling eastern dresses. It replaces a pure-WhatsApp order flow for customers who want single items instead of wholesale-catalog quantities.

**Full spec:** `../mip-business/specs/marketinpakistan-store-implementation-plan.md` — phased build-out, current phase, and why each phase is sequenced the way it is.
**Architecture reference:** `../mip-business/RETAIL_STORE_ARCHITECTURE.md` — schema, stack, rationale.

## Current status (update this section at the end of each phase)

**Revised 2026-09-27, superseding the original Phase 1 plan below.** The business owner clarified the actual requirement: customers must complete a real checkout, the business must receive orders by **email**, and WhatsApp is for **customer support only**, not order placement. This collapses the original "Phase 1 = WhatsApp-CTA-only demand test, no DB, gated before Phase 2" sequencing — checkout + order email shipped directly instead. Phase 0 (fixing the WhatsApp closing script) remains explicitly skipped by the business owner's decision, but is now less load-bearing since WhatsApp is no longer the order-closing channel.

**What's implemented:**
- Cart: `app/lib/cart.ts` (`useSyncExternalStore`-backed, persisted to `localStorage` as `mip_cart`) — supports multiple products/sizes in one order, matching the "customers buy single items across multiple catalogs" requirement
- Product page (`app/product/[slug]/page.tsx`): `AddToCartForm` (size + quantity) replaces the old per-product "Order on WhatsApp" button
- `/cart` and `/checkout`: checkout form (name, phone required, email optional, address, city) posts to `app/api/orders/route.ts`
- `app/api/orders/route.ts`: validates the order, emails it to `ORDER_NOTIFICATION_EMAIL` via Resend (`resend` npm package). **Working** (real test orders verified on 2026-09-27 and 2026-09-30). If `RESEND_API_KEY` / `ORDER_NOTIFICATION_EMAIL` are missing it fails gracefully — before touching stock — with a "not configured, contact us on WhatsApp instead" message and a WhatsApp fallback link
- Customer confirmation email is sent best-effort (non-blocking) when the customer provides an email — **will not actually deliver** until `marketinpakistan.shop` is verified as a sending domain with Resend (a Resend account without domain verification can only deliver to the account's own registered address)
- No order persistence — an order exists only as an email (the database only holds products, see below); there is no admin view of past orders yet. This is an intentional simplification versus the original architecture doc's DB-first Phase 2, chosen to ship the actual requirement (checkout + email) fast; revisit once order volume makes "email is the only record" a real problem
- WhatsApp is now support-only: `app/components/general-whatsapp-button.tsx`, shown in the site header and as a fallback on checkout errors — not tied to placing an order
- Products live in **Neon Postgres** (added 2026-09-30, free plan; Vercel integration resource `neon-charcoal-yacht`, `DATABASE_URL` in all 3 Vercel environments). Schema/seed in `db/schema.sql`, `db/seed.sql`; apply with `node --env-file=.env.local scripts/apply-sql.mjs <file.sql>`. `app/data/products.ts` no longer exists. All queries are in `app/lib/products.ts` (server-only); storefront pages read from it and refresh every 5 minutes or immediately after an admin save (`revalidatePath("/", "layout")`). There is no separate dev database: local dev and production share the same Neon DB, so test carefully and clean up test rows
- **Admin panel** at `/admin` (design canvas: https://claude.ai/artifact/LKgpyunMJ1UYQxam7VLM3y; spec: `specs/admin-panel-implementation-plan.md`). One shared password (`ADMIN_PASSWORD`), signed httpOnly session cookie (`SESSION_SECRET`, `jose`; token logic in `app/lib/session-token.ts`, cookie helpers `requireAdmin()`/`isAdmin()` in `app/lib/session.ts`). `proxy.ts` only does an optimistic redirect — **every** admin page, server action (`app/admin/actions.ts`) and route handler must call `requireAdmin()`/`isAdmin()` itself. Login has a 1 s delay on a wrong password but no lockout, so keep the password long. Features: add/edit/hide/delete products, volume (`catalog`) + collection, quantity, up to 8 photos. Hidden products are removed from the store; deleted ones are gone for good (their Cloudinary files are NOT deleted)
- Photos: browser uploads straight to Cloudinary (cloud `duwktiwnj`, folder `products/`) using a server-signed request from `POST /api/admin/cloudinary-sign` (`app/lib/cloudinary.ts`); only URLs from our own Cloudinary account are accepted when saving. Store images go through `optimizedImage()` (`app/lib/images.ts`, adds `f_auto,q_auto,w_…`)
- Orders are server-authoritative (`app/api/orders/route.ts`, `app/lib/orders.ts`): the browser only sends slug/size/quantity; name and price come from the DB. Hidden/deleted/sold-out/price-changed items return 409 `corrections` and the checkout applies them to the cart (`reconcileCart()` in `app/lib/cart.ts`) without ordering. Stock is reserved in one atomic SQL statement and restored if the notification email fails. **Known gap:** orders are not saved, so cancelling a customer's order does not put stock back — someone must raise the quantity in the admin edit form. Fix later with an orders table + Cancel button
- Product photo gallery (added 2026-09-30; spec `specs/product-photo-gallery-implementation-plan.md`, mockups in the same design canvas): `app/components/product-gallery.tsx` on the product page — swipeable scroll-snap strip (phone) with counter, arrows, dots and thumbnails; vertical thumbnail column on desktop; tap the main photo for a full-screen zoom built on a native `<dialog>` (tap toggles 2x, swipe/arrow keys/arrows/thumbnails change photo, Esc/Close, page scroll locked while open, fit-to-screen reuses the 900 px image and only real zoom loads 1600 px). Single-photo products show no controls. Product cards show an "N photos" badge for 2+ photos. The first photo is the cover everywhere (cards, WhatsApp/OG image); in the admin uploader "Make cover" and move earlier/later buttons set the order. No per-photo captions. Pinch-zoom relies on the browser and iOS Safari swipe/zoom behaviour has only been checked on desktop Chrome emulation — check on a real phone after changes
- Sold-out state: quantity 0 shows a "Sold out" badge, hides Add to Cart, and the quantity box is capped at stock
- `?src=` attribution (`app/components/source-tracker.tsx`) still captured into `localStorage`, now passed into the order email's `Source:` field server-side — no longer dependent on the business owner manually reading it off a WhatsApp message
- Delivery charges (added 2026-09-29): `app/lib/pricing.ts` — quantity-tiered per the owner's quote (1 dress PKR 300, 2–4 dresses PKR 350, 5+ dresses free, based on total quantity summed across the whole cart, not distinct product lines). Split out of `app/lib/cart.ts` because that file is `"use client"` and `app/api/orders/route.ts` needs a server-side value import — importing a function from a `"use client"` module into a Route Handler compiles but throws at runtime (RSC client-reference transform). Shown as a Subtotal/Delivery/Total breakdown on `/cart`, `/checkout`, the post-order confirmation screen, and in both order emails; verified end-to-end with a headless-browser walkthrough at each tier boundary plus a real test order
- Winter Clearance Sale (added 2026-09-29): products carry `collections: string[]` (DB column; `getCollectionProducts()` in `app/lib/products.ts`; collections themselves are rows in the `collections` table, so a new one such as Summer is an SQL insert until the admin panel gets a Collections screen); dresses tagged `winter-clearance` appear on `/winter-clearance` grouped by `catalog` (volume) and in the home hero collage. To add a volume's dresses, use the admin panel (Volume field + Winter Clearance Sale collection). Header has a "Winter Clearance Sale" link first, a mobile hamburger menu (closes on any route change — open state is keyed to the pathname, no effect), and the Cart link only shows when the cart is non-empty. All dresses are still PKR 3000 — no sale pricing/strike-through yet

## Conventions

- Next.js App Router + TypeScript + Tailwind CSS
- Plain `<img>` tags, not `next/image` — images are served from Cloudinary with URL transforms via `optimizedImage()`, so there's no need for Next's own image optimization pipeline
- Cart state uses `useSyncExternalStore`, not `useState` + `useEffect` — this repo's ESLint config (`react-hooks/set-state-in-effect`, part of the React Compiler rule set) errors on synchronous `setState` inside effects, so reading/writing `localStorage`-backed state should go through an external store, not an effect
- Deploy by pushing to `main` on GitHub — Vercel auto-deploys it to production (marketinpakistan.shop). Don't make dummy "trigger rebuild" commits; if the live site looks stale, run `npx vercel ls` to see whether a deployment was created, and use `npx vercel --prod` only as a manual fallback
- `npx vercel integration add neon` left `.agents/`, `.claude/settings.local.json` and `skills-lock.json` in the repo root; they are untracked on purpose — don't commit them
- No payment gateway — Cash on Delivery, confirmed manually after checkout (by phone/WhatsApp), matches how the business already operates
